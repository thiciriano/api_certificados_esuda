Primeira Entrega — Concepção Técnica + MVP Inicial

Itens que eu incluiria na Primeira Entrega:

1. Contexto do problema

Antes dos requisitos, cada grupo deve explicar o problema do sistema.

Exemplo:

A instituição precisa de uma API para gerenciar eventos acadêmicos, inscrições, usuários e emissão de certificados, substituindo controles manuais por uma solução centralizada.

Eles devem responder:
 - Qual problema o sistema resolve?
 - Quem vai usar?
 - Qual o objetivo da API?
 - Qual o escopo da primeira versão?

Isso ajuda a evitar projeto sem direção.

---

2. Definição dos perfis de usuário

Mesmo que a autorização só seja implementada na segunda unidade, eles já precisam definir os perfis agora.

Exemplo:

| Perfil       | Descrição                               |
| ------------ | --------------------------------------- |
| Admin        | Gerencia usuários, eventos e inscrições |
| Organizador  | Cria e gerencia eventos                 |
| Participante | Consulta eventos e realiza inscrições   |

Isso prepara a base para JWT e controle de acesso na segunda unidade.

---

3. Regras de negócio

Esse é um dos pontos mais importantes para deixar o projeto com nível de mercado. Deve ter no minimo 10 regras de negócio.

Exemplos:
 - Um usuário não pode se inscrever duas vezes no mesmo evento.
 - Um evento não pode ultrapassar a capacidade máxima.
 - Apenas administradores podem excluir eventos.
 - Um participante só pode cancelar a própria inscrição.
 - Não é permitido cadastrar evento com data passada.
 - Um certificado só pode ser emitido para participante inscrito.

Sem regra de negócio, o projeto vira apenas CRUD simples.

---

4. Entidades principais do sistema

Eles devem definir quais tabelas/recursos existirão.

Exemplo para sistema de eventos:
 - Usuário
 - Evento
 - Inscrição
 - Certificado
 - Categoria ou Atividade

Cada grupo deve explicar por que escolheu essas entidades.

---

5. Modelo de dados / DER

Obrigatório.

Eles devem entregar um modelo inicial do banco contendo:
 - tabelas;
 - campos;
 - chaves primárias;
 - chaves estrangeiras;
 - relacionamentos;
 - cardinalidade.

Esse item casa diretamente com as aulas de persistência, relacionamentos e migrations.

---

6. Dicionário de dados

Além do DER, peça uma tabela explicando os campos.

Exemplo:

| Entidade  | Campo       | Tipo   | Obrigatório | Regra                |
| --------- | ----------- | ------ | ----------- | -------------------- |
| Usuário   | email       | string | Sim         | Único e válido       |
| Evento    | capacidade  | int    | Sim         | Maior que zero       |
| Evento    | data_evento | date   | Sim         | Não pode ser passada |
| Inscrição | status      | string | Sim         | ativa/cancelada      |


---

7. Contratos de entrada e saída da API

Além de dizer as rotas, eles devem definir o que cada rota recebe e retorna.

Exemplo:

POST `/api/v1/eventos`

Entrada

{
  "titulo": "Workshop de FastAPI",
  "descricao": "Evento prático sobre APIs",
  "data_evento": "2026-09-10",
  "capacidade": 50
}

Saída

{
  "id": 1,
  "titulo": "Workshop de FastAPI",
  "descricao": "Evento prático sobre APIs",
  "data_evento": "2026-09-10",
  "capacidade": 50,
  "status": "ativo"
}

Isso conecta diretamente com Pydantic, validação e Swagger.

---

8. Definição dos status codes

Devem informar quais status codes serão usados.

Exemplo:

| Situação                 | Status     |
| ------------------------ | ---------- |
| Registro criado          | 201        |
| Consulta realizada       | 200        |
| Atualização realizada    | 200 ou 202 |
| Exclusão realizada       | 204        |
| Registro não encontrado  | 404        |
| Erro de regra de negócio | 400        |
| Não autenticado          | 401        |
| Sem permissão            | 403        |
| Erro de validação        | 422        |

Isso ajuda muito a profissionalizar o projeto.

---

9. Padrão de resposta e erro

Definir um padrão para respostas de sucesso e erro.

Exemplo de sucesso:

{
  "success": true,
  "data": {},
  "message": "Operação realizada com sucesso."
}

Exemplo de erro:

{
  "detail": "Evento não encontrado."
}

Não precisa obrigar todos a usarem o mesmo padrão, mas deve justificar o padrão escolhido.

---

10. Matriz de permissões

Mesmo que a implementação fique para a segunda unidade, a matriz já deve ser planejada.

Exemplo:

| Funcionalidade         | Admin | Organizador | Participante |
| ---------------------- | ----: | ----------: | -----------: |
| Criar evento           |   Sim |         Sim |          Não |
| Excluir evento         |   Sim |         Não |          Não |
| Listar eventos         |   Sim |         Sim |          Sim |
| Inscrever-se em evento |   Não |         Não |          Sim |
| Emitir certificado     |   Sim |         Sim |          Não |

Esse item vai facilitar muito a aula de autorização.

---

11. Estrutura inicial do projeto

Devem apresentar a estrutura de pastas planejada.

Exemplo:

app/
├── api/
│   └── v1/
│       ├── routers/
│       └── api.py
├── core/
│   ├── config.py
│   ├── security.py
│   └── deps.py
├── models/
├── schemas/
├── services/
├── repositories/
├── database/
├── tests/
└── main.py


Na primeira unidade, você pode exigir pelo menos:

api/
core/
models/
schemas/
main.py

E deixar `services`, `repositories` e `tests` como evolução.

---

12. Tecnologias escolhidas e justificativa

Expliquem o papel de cada tecnologia.

Exemplo:

| Tecnologia          | Uso no projeto                          |
| ------------------- | --------------------------------------- |
| FastAPI             | Construção da API REST                  |
| PostgreSQL          | Banco de dados relacional               |
| SQLAlchemy/SQLModel | Mapeamento ORM                          |
| Alembic             | Migrations                              |
| Pydantic            | Validação de dados                      |
| JWT                 | Autenticação na segunda entrega         |
| Pytest              | Testes automatizados na segunda entrega |

Isso faz o aluno entender a stack, não apenas copiar.

---

13. Estratégia de banco e migrations

Na primeira entrega, eles devem definir:
 - qual banco será usado;
 - quais tabelas iniciais;
 - quais relacionamentos;
 - se haverá migrations;
 - qual será a migration inicial.

Se possível, peça uma migration inicial já criada.

Exemplo:

alembic revision --autogenerate -m "cria tabelas iniciais"

---

14. Backlog do projeto

Eles devem criar um backlog simples, com no minimo 10:

| ID   | História/User Story                                        | Prioridade |
| ---- | ---------------------------------------------------------- | ---------- |
| US01 | Como participante, quero me cadastrar para acessar eventos | Alta       |
| US02 | Como admin, quero criar eventos acadêmicos                 | Alta       |
| US03 | Como participante, quero me inscrever em eventos           | Alta       |
| US04 | Como organizador, quero listar inscritos                   | Média      |

---

15. Critérios de aceitação

Cada funcionalidade principal deve ter critérios de aceite, no minimo 10.

Exemplo:

Cadastro de usuário

Critérios:
 - Deve exigir nome, e-mail e senha.
 - Não deve permitir e-mail duplicado.
 - A senha não deve ser retornada na resposta.
 - Deve retornar status `201` ao cadastrar com sucesso.
 - Deve retornar erro ao cadastrar e-mail inválido.

Isso ajuda os alunos a pensarem como QA e como desenvolvedores.

---

16. Protótipo inicial da API

Além da documentação, eles devem entregar um MVP técnico inicial com:
 - projeto FastAPI criado;
 - Swagger abrindo;
 - conexão inicial com banco;
 - pelo menos uma entidade com CRUD básico;
 - schemas Pydantic;
 - models do banco;
 - rotas organizadas;
 - repositório GitHub.

Não precisa estar completo ainda, mas precisa existir.
